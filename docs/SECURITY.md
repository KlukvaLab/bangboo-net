# Устойчивость C ABI (hardening)

Этот документ описывает защиту библиотеки от неправильного
использования и внутренних сбоев. Реализация — `src/ffi.rs`
(catch_unwind, билеты жизни, Mutex-дескрипторы), `src/tls.rs`
(владение AuthContext, RAII для fd), `src/init.rs` (nb_shutdown),
`src/limits.rs` (лимиты), `src/error.rs` (слоты без деструкторов).
Проверяется тестом `tests/misuse.c`.

## 1. Паники Rust не пересекают границу FFI

Unwind через `extern "C"` — неопределённое поведение: ломает стек
C++/ART (Android), может уронить процесс хоста. Каждый экспорт
`nb_*` обёрнут в `std::panic::catch_unwind`:

* паника превращается в возврат `-14` (`Panic`) / `NULL`;
* сообщение (включая текст паники) — в `nb_last_error_message()`;
* дескриптор остаётся валидным для close, но состояние могло быть
  нарушено — рекомендуется закрыть его и открыть новый.

Отравленные Mutex/RwLock не блокируют библиотеку навсегда: блокировки
восстанавливаются через `unwrap_or_else(|e| e.into_inner())`.

## 2. Владение и время жизни

* **AuthContext → TlsStream** (было: владение в стеке connect-функции).
  NSS может вызвать auth-колбэк и после handshake (ренеготиация
  TLS 1.2), поэтому контекст живёт столько же, сколько сокет.
  Освобождение — строго ПОСЛЕ `PR_Close`: PR_Close может реентерабельно
  входить в NSS. Это устраняет UAF при повторных вызовах NSS.
* **RAII для PRFileDesc** (`FdGuard`): дескриптор закрывается в `drop`
  на любом пути выхода — включая панику между созданием сокета и
  успехом. Утечки TCP/SSL-дескрипторов при ошибках конфигурации
  исключены структурно.
* **`NbH3Request::conn`** — больше не висячий указатель: соединение
  держит реестр своих запросов, `nb_h3_close` атомарно обнуляет `conn`
  у всех (осиротивание). Запросы после закрытия соединения возвращают
  `-9 Closed` вместо чтения освобождённой памяти; `nb_h3_req_free`
  работает в любом порядке относительно `nb_h3_close`.
* **Алгоритмы сжатия сертификатов** (RFC 8879): структуры и имена NSS
  хранит в каждом сокете до его закрытия, поэтому они создаются РОВНО
  ОДИН РАЗ на процесс (`OnceLock` в `profile.rs`). Раньше `Box::leak` +
  `CString::into_raw` утекали на каждое TLS-подключение — по шесть
  аллокаций, включая неудачные попытки Happy Eyeballs.
* **Мёртвый API удалён**: `nb_tls_ech_retry_configs` удалён — при
  `-12 EchRetryWithEch` хэндл не возвращается (NULL), функция была
  недостижима по контракту. Ретрай ECH — через свежий конфиг из DNS
  HTTPS-записи (задокументированный поток).

## 3. Потокобезопасность и close

* Состояние каждого дескриптора — под `Mutex`: одновременные вызовы из
  разных потоков сериализуются. Гонок данных на внутреннем состоянии
  нет.
* Жизненный цикл — через «билет» (`Arc<Ticket>` c `RwLock`): операции
  держат read-lock, `close/free` — write-lock и освобождают `Box`
  только под ним. Операция, начавшаяся до close, дорабатывает на
  корректной памяти; close дождётся её окончания.
* `close/free` принимают **адрес указателя** (`NbTls **`) и обнуляют
  его. Повторный вызов — no-op. Двойной close/free невозможен при
  использовании этого паттерна.
* Порядок блокировок фиксирован (ticket → requests → inner),
  вложенных requests+inner нет — дедлоков нет.

Что остаётся на контракте вызывающего (как в любой C-библиотеке):
не передавать ОДИН указатель-копию в поток, который использует его
после того, как другой поток уже вернулся из close (сам вызов close
синхронизирован, но копию сырого указателя библиотека обнулить не
может).

## 4. Лимиты размеров (анти-DoS)

`nb_set_limits(max_http1_body, max_ws_message, max_h3_response)`
(байты, `0` = без лимита, по умолчанию 64 МиБ, глобально на процесс):

| Что ограничено | Где проверяется | Ошибка |
|---|---|---|
| тело HTTP/1.1 (Content-Length, chunked, до-EOF) | `http1.rs::read_body` | -15 |
| кадр WS и сумма фрагментов (приём и передача) | `ws.rs::recv/send` | -15 |
| тело HTTP/3-ответа (на запрос) | `quic.rs::drain_events` + STOP_SENDING | -15 |

Раньше сервер, объявляющий сколь угодно большое тело (или бесконечная
фрагментация WS), мог занять всю память процесса.

## 5. Буферы вызывающего

Все функции, копирующие данные наружу, при нехватке места возвращают
`-13 BufferTooSmall` и записывают точный нужный размер в out-параметр
`needed` (для строк — с NUL). Прежняя схема `-(need+1)` коллизировала
с кодами ошибок (например, «нужно 3 байта» выглядело как NotInitialized).
Дополнительно:

* NULL-буфер с ненулевой потребностью — ошибка, а не запись по NULL
  (раньше `nb_http1_response_header` мог записать NUL по нулевому
  указателю при большой заявленной ёмкости);
* `nb_ws_recv` при too-small НЕ теряет сообщение — оно возвращается
  в очередь и придёт следующим вызовом.

## 5a. Свежесть ошибки (многопоточность/JNA)

Слот последней ошибки очищается **на входе каждой операции** `nb_*`
(в `nb_guard`): слот всегда отражает именно последний вызов в этом
потоке. `nb_last_error_code()` и `nb_last_error_message()` оба
НЕразрушающие — читайте в любом порядке, сколько угодно раз; после
успешной операции `nb_last_error_code() == 0`. (Раньше message
очищал слот, а code — нет: после любой успешной операции code
показывал протухшую ошибку предыдущего вызова.)

## 5b. Дефолты и границы таймаутов

Все `timeout_ms`: `0` → 30000 мс; значения выше 24 часов урезаются
до 24 часов (`ffi.rs::dur`). Причина: `PR_MillisecondsToInterval`
принимает PRUint32 и на значениях порядка `u32::MAX` переполняется,
а `Instant + Duration` на таких величинах может паниковать. Раньше
`0` превращался в 1 мс — операции «с дефолтным» таймаутом падали
ложным Timeout. `NbConnectOptions.port = 0` → 443.

## 5c. QUIC-драйвер не busy-loop'ит

Если пир закрыл соединение, `process_output` не даёт ни датаграмм,
ни таймеров — старый цикл крутился вхолостую до дедлайна (100% CPU).
Теперь: `drive_until` проверяет `Http3State::Closed` и возвращает
`-9 Closed`; отсутствие таймеров (`Output::None`) даёт bounded-ожидание
по сокету (≤20 мс) вместо мгновенного возврата в цикл.

## 5d. HTTP/1.1 keep-alive

`nb_http1_fetch` шлёт `Connection: keep-alive` и читает тело РОВНО
по Content-Length/chunked (включая трейлеры после последнего chunk —
без их потребления соединение рассинхронизировалось бы): несколько
fetch по одному дескриптору без переподключения, как Firefox. EOF
до/в середине ответа — `-9 Closed` (раньше -10 ProtocolError).

## 6. nb_shutdown и выгрузка .so (dlclose)

`nb_shutdown()` — настоящий (раньше был no-op):

* сбрасывает глобальный верификатор (rustls-webpki);
* если NSS подняла библиотека (а не хост-приложение) — вызывает
  `NSS_Shutdown()`. При незакрытых дескрипторах NSS отказывает
  (SEC_ERROR_BUSY): возвращается ошибка, dlclose в этом случае нельзя;
* после успешного shutdown возможен повторный `nb_init` (особый случай:
  OnceLock внутри nss-rs не умеет re-init — библиотека поднимает NSS
  напрямую через `NSS_NoDB_Init`, см. `init.rs::ensure_nss`).

Для dlclose на Android:

* все thread-local слоты библиотеки — `Copy`-типы с const-инициализацией
  (фиксированные буферы вместо `String`/`CString`): TLS-деструкторы НЕ
  регистрируются, поэтому вызов деструкторов выгруженной библиотеки
  (краш на bionic < API 28) невозможен;
* atexit-обработчики NSS не регистрируются (NoDB-режим); on-exit
  обработчики dlopen-нутой .so glibc/bionic снимают сами;
* правильный порядок выгрузки: закрыть все дескрипторы →
  `nb_shutdown()` (должен вернуть 0) → `dlclose`.

## 7. Что проверяет tests/misuse.c

1. NULL-аргументы во всех функциях → -2 (не segfault);
2. close/free с NULL и с NULL-слотом — no-op;
3. too-small буферы → -13 + needed;
4. двойной close/free всех дескрипторов — no-op;
5. запрос H3 после закрытия соединения → -9 (не UAF);
6. лимит 16 байт на тело HTTP/1.1 → -15 MessageTooLarge;
7. дефолты контракта: `port=0` → 443, `timeout_ms=0` → 30000
   (реальное подключение с нулевыми полями);
8. свежесть ошибки: после успешной операции `nb_last_error_code()==0`;
9. `nb_shutdown` → 0, использование после → -3, повторный `nb_init`
   и новое соединение — работают.

`tests/smoke.c` дополнительно проверяет keep-alive: два
`nb_http1_fetch` по одному дескриптору, оба 200.

## Гарантии, которые НЕ предоставляются

* Произвольная запись по мусорному указателю (не NULL): библиотека не
  может отличить «дескриптор, освобождённый ранее в другом порядке» от
  валидного — это верно для любой C-библиотеки с непрозрачными
  дескрипторами.
* Защита от использования дескриптора потоком, держащим копию сырого
  указателя, после возврата close в другом потоке (см. §3).
